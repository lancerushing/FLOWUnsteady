## Project Overview

FLOWUnsteady is an open-source variable-fidelity aerodynamics and aeroacoustics solver for multirotor aircraft and wind energy. It's built on the reformulated vortex particle method (rVPM), a meshless CFD approach that solves the LES-filtered incompressible Navier-Stokes equations in their vorticity form.

The codebase is written in **Julia** and integrates multiple aerodynamic modeling approaches: vortex lattice method (VLM), lifting line, blade elements, 3D panel method, and rVPM, with acoustic prediction through FW-H and BPM codes.

### Known Issues

**Python 3.12+ Incompatibility**: The `AirfoilPrep` dependency uses Python's deprecated `imp` module which was removed in Python 3.12. If you have Python 3.12+:
- Use Python 3.11 or earlier with PyCall: `ENV["PYTHON"] = "/usr/bin/python3.11"; Pkg.build("PyCall")`
- Or wait for AirfoilPrep to be updated to use `importlib` instead of `imp`

### Docker Development Environment

Docker provides a consistent development environment with all system dependencies pre-installed. This is the **recommended approach** for new developers or those with Python 3.12+ installed.

#### Quick Setup

Run the automated setup script to build the image and install Julia packages:

```bash
./docker-setup.sh
```

This builds a custom Docker image with:
- Julia 1.12.2 on Debian Trixie
- Build tools (CMake, GCC, OpenMPI) for ExaFMM compilation
- Python 3.11 (compatible with AirfoilPrep)
- Required Python packages (matplotlib, scipy, mpmath)

#### Interactive Development Workflow

For active development with a persistent container:

```bash
# Build and start container
docker compose up -d

# Enter interactive shell
docker compose exec flowunsteady bash

# Inside container: install Julia packages (if not done during setup)
julia --project setup.jl

# Run tests
julia --project -e "using Pkg; Pkg.test()"

# Stop container when done
docker compose down
```

Your local directory is mounted at `/workspace/FLOWUnsteady`, so all changes are synced between host and container.

## Architecture and Key Components

### Module Structure
The main module `FLOWUnsteady` is defined in `src/FLOWUnsteady.jl` and imports from several specialized FLOW Lab packages:
- **FLOWVPM**: Reformulated Vortex Particle Method solver for computing velocity and forces in the wake
- **FLOWVLM**: Vortex Lattice Method for wing aerodynamics
- **GeometricTools**: Geometric operations and coordinate transformations
- **VSPGeom**: OpenVSP geometry integration
- **FLOWNoise**: Aeroacoustic noise prediction
- **BPM**: Blade Pressure Mode noise prediction

### Core Types and Concepts

#### 1. **Vehicle Types** (`src/FLOWUnsteady_vehicle.jl`)
All vehicles inherit from `AbstractVehicle{N, M, R}`:
- `N`: Number of tilting systems (e.g., rotors that can tilt)
- `M`: Number of rotor systems
- `R`: Real type for numerical precision

Key implementations:
- **UVLMVehicle**: Unsteady VLM vehicle for wing simulations with VPM coupling
- **QVLMVehicle**: Quasi-steady VLM vehicle for faster, low-fidelity simulations

Vehicle responsibilities include:
- Managing position, velocity (`V`), and angular velocity (`W`)
- Hosting rotor systems and tilting systems
- Providing kinematic interface for time-stepping

#### 2. **Simulation Interface** (`src/FLOWUnsteady_simulation_types.jl`)
The `Simulation` type connects vehicles and maneuvers:
```
Simulation(vehicle, maneuver, Vref, RPMref, ttot; Vinit=..., Winit=...)
```
Parameters:
- `vehicle`: The aircraft/vehicle being simulated
- `maneuver`: Describes the flight path/motion (tilting angles, velocity profile)
- `Vref`: Reference velocity
- `RPMref`: Reference rotor speed
- `ttot`: Total simulation time

Concrete implementations handle solver dispatch:
- **UVLMSimulation** (`FLOWUnsteady_simulation_types_unsteady.jl`): Full VPM+VLM coupling with unsteady aerodynamics
- **QVLMSimulation** (`FLOWUnsteady_simulation_types_quasisteady.jl`): Quasi-steady approximation (faster, lower fidelity)

Time-stepping functions:
- `nextstep_kinematic()`: Updates vehicle position and orientation
- `precalculations()`: Updates rotor RPM and pitch angles, calculates kinematic wake
- Solver-specific functions for aerodynamic solution

#### 3. **Rotors** (`src/FLOWUnsteady_rotor.jl`)
Rotors are modeled as actuator line elements using blade element theory:
- Automatic airfoil lookup table generation via XFOIL
- Support for variable RPM and pitch control
- Thrust and torque calculation
- Optional vortex shedding into the flow field

#### 4. **Processing and Post-processing**
- **Force processing** (`src/FLOWUnsteady_processing_force.jl`): Calculates aerodynamic forces from flow field
- **Noise prediction** (`src/FLOWUnsteady_noise_wopwop.jl`, `src/FLOWUnsteady_noise_bpm.jl`): Acoustic analysis
- **Post-processing** (`src/FLOWUnsteady_postprocessing.jl`): Data analysis and visualization
- **Monitoring** (`src/FLOWUnsteady_monitors.jl`): Runtime solution tracking

### Data Flow in a Simulation

1. **Setup**: Create a `Vehicle` with geometry and rotors, define a `Maneuver`
2. **Time Loop**: For each time step:
   - `precalculations()`: Update rotor states, shed wake particles
   - `nextstep_kinematic()`: Move vehicle, tilt systems
   - Solver step: Call FLOWVPM to compute velocity field and aerodynamic forces
   - `postprocessing()`: Compute noise, save data
3. **Output**: VTK files for visualization, force/power histories, acoustic predictions

### Fidelity Levels

The framework supports variable-fidelity simulations:
- **Low fidelity**: Coarse particle spacing, few time steps (free-wake method equivalent)
- **Mid fidelity**: Balanced discretization, iterative wake coupling
- **High fidelity**: Fine mesh, LES-level resolution with VPM

Fidelity is controlled through simulation parameters:
- Particle spacing (domain and VPM resolution)
- Time stepping (implicit vs explicit, sub-stepping)
- Wake coupling (uncoupled vs coupled VPM-VLM)

## Common Development Tasks

### Adding a New Maneuver
1. Create a new maneuver type inheriting from `AbstractManeuver` in `src/FLOWUnsteady_maneuver.jl`
2. Implement required functions: `get_angles()`, `calc_dV()`, `calc_dW()`
3. Pass it to `Simulation()` constructor

### Extending Vehicle Types
1. Create a new concrete type inheriting from `AbstractVehicle{N, M, R}`
2. Implement all required functions (velocity getters/setters, kinematic update, etc.)
3. Create corresponding simulation type in `FLOWUnsteady_simulation_types_*.jl`
4. Add solver dispatch in `FLOWUnsteady_simulation.jl`

### Modifying Aerodynamic Models
- VLM-specific: `src/FLOWUnsteady_vehicle_vlm.jl`
- Rotor models: `src/FLOWUnsteady_rotor.jl`
- Force calculation: `src/FLOWUnsteady_processing_force.jl`

## Testing Strategy

The test suite in `test/` uses Julia's `Test` framework with testsets:
- `test/runtests.jl`: Main test entry point
- `test/test_sweptwing.jl`: Isolated wing and coupled VPM-VLM validation tests

Current tests verify:
- VLM solver on isolated wing (with/without regularization)
- VPM-VLM coupling
- Kinematic velocity effects
- Quasi-steady solver

Add new tests by creating `test/test_*.jl` files and including them in `runtests.jl`.

## Performance Considerations

- **Parallelization**: CPU parallelization via OpenMP (no MPI support)
- **Fast-Multipole**: ExaFMM acceleration for N-body VPM calculations
- **Memory**: Large-scale simulations may require significant RAM due to particle field storage
- **Time stepping**: Explicit RK3 integration requires CFL-type constraint on dt (handled automatically)

## Code Quality and Improvement Areas

This codebase was developed by mechanical and aerospace engineering students and has opportunities for improvement in:

- **Error handling**: Missing validation for user inputs, file operations, and numerical computations. Watch for unhandled edge cases.
- **Path handling**: Look for hardcoded absolute paths and platform-specific path assumptions. Paths should be relative and cross-platform compatible.
- **Hardcoded values**: Magic numbers and fixed parameters should be configurable. Look for values that could be function arguments or configuration options.
- **Robustness**: Operations involving file I/O, external packages, and numerical algorithms may lack proper error checks or fallbacks.

When making modifications, prioritize improvements in these areas alongside the requested changes.
